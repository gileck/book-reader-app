# 5.3 Synchronization

## Overview

Perfect synchronization between audio playback and visual text highlighting is critical for the reading experience. This section explains how word-level highlighting works and why it's accurate.

## How Synchronization Works

**The Challenge:**
- Audio plays continuously at exact timing
- Text must highlight precisely as words are spoken
- Different voices have different pacing
- Words vary in length and complexity

**The Solution:**
- TTS providers return timing metadata for each word
- System matches current audio time to word timing
- Highlight updates in real-time during playback
- Adjustable offset compensates for variations

> **📘 Technical Deep Dive:** See [Word-Audio Synchronization](technical/word-audio-synchronization.md) for the complete implementation including SSML mark generation, timepoint extraction, and real-time synchronization algorithms.

## Word Timing Metadata

**What Providers Return:**
- Start time for each word (in seconds)
- End time for each word
- Word index in sentence
- Sometimes: Phoneme-level timing (advanced)

**Example:**
- Word "Hello" starts at 0.0s, ends at 0.3s
- Word "world" starts at 0.3s, ends at 0.7s
- Word "this" starts at 0.7s, ends at 0.9s

**Variations by Provider:**
- Google: Timepoint data per word
- Polly: Speech marks with timing
- ElevenLabs: Character-level timing (converted to words)

## Real-Time Highlight Updates

**How It Works:**
1. Audio playback starts
2. System checks current audio time (~every 250ms)
3. Finds which word contains current time
4. Highlights that word if different from previous
5. Un-highlights previous word
6. Repeats until sentence ends

**Why 250ms Updates:**
- Frequent enough for smooth highlighting
- Not so frequent it causes performance issues
- Balances responsiveness and efficiency
- Imperceptible delay to users

**Optimization:**
- Only updates when word actually changes
- No unnecessary DOM manipulations
- Smooth transitions between words
- 60fps visual performance

## Timing Offset Feature

**Why It's Needed:**
- Different voices have different timing characteristics
- Neural voices may have slight delays vs standard
- Provider timing accuracy varies
- Browser audio buffering introduces latency

**User Control:**
- Adjustable: -500ms to +500ms
- Default: 0ms (no offset)
- Fine-tunes synchronization
- Per-user preference (saved)

**Use Cases:**
- Audio seems ahead: Negative offset (e.g., -200ms)
- Audio seems behind: Positive offset (e.g., +100ms)
- Fine-tuning for perfect sync
- Voice-specific adjustments

## Edge Cases

**Very Short Words:**
- Words like "I", "a" may have <50ms duration
- System ensures minimum highlight duration (50ms)
- Prevents invisible highlights
- Maintains visual continuity

**Long Words:**
- Words >20 characters may exceed container
- System adjusts or switches to line mode
- Prevents layout breaks
- Maintains readability

**Punctuation:**
- Periods, commas not typically highlighted
- Focus on actual word content
- Clean visual appearance
- Maintains reading flow

**Numbers and Dates:**
- "2024" spoken as "twenty twenty-four"
- Provider handles pronunciation
- Timing matches spoken words
- May differ from written form

## Why Synchronization Is Accurate

**Provider Quality:**
- Professional TTS engines
- Accurate word timing data
- Consistent across playback speeds
- Tested and refined algorithms

**System Optimization:**
- High-frequency timing checks
- Efficient word matching
- Smooth DOM updates
- Hardware acceleration

**User Adjustability:**
- Timing offset for fine-tuning
- Different modes (word vs line)
- Works across all voices
- Saved preferences

## Visual Smoothness

**No Flicker:**
- Word highlights transition smoothly
- No flash between words
- Clean visual appearance
- Professional quality

**Performance:**
- 60fps highlighting
- No lag or stutter
- Works during scrolling
- Efficient rendering

> **📘 Technical Deep Dive:** See [Word Highlighting CSS](technical/word-highlighting-css.md) for the performance-optimized CSS implementation that achieves 60fps.

**Responsiveness:**
- Immediate response to playback changes
- Pause/resume preserves position
- Seek/skip updates instantly
- Smooth across all modes

## Known Limitations

**Timing Accuracy:**
- Typical accuracy: ±50ms
- Varies by provider and voice
- Adjustable with offset
- Generally imperceptible

**Provider Differences:**
- Google: Very accurate
- Polly: Good accuracy
- ElevenLabs: Excellent, character-level

**Edge Cases:**
- Very fast playback (>1.8x) may reduce accuracy
- Some voices better than others
- Complex punctuation may affect timing
- Rare words may have less accurate timing
