# 5.2 Technical Overview

## How TTS Works

This section explains how the TTS system works from a product perspective, focusing on concepts that affect user experience.

## Audio Generation Flow

**The Process:**
1. User clicks play on a sentence
2. System checks if audio already cached
3. If cached: Plays immediately (instant)
4. If not cached:
   - Text sent to selected TTS provider API
   - Provider generates audio with word timing data
   - Audio received and cached locally
   - Playback begins
5. Word highlighting syncs with audio timing

**Why This Matters:**
- First play may have brief delay (generating audio)
- Subsequent plays are instant (cached)
- Changing voice/speed requires regeneration
- Network issues only affect first play

## Caching System

**What Gets Cached:**
- Generated audio files
- Word timing metadata
- Provider and voice used
- Playback speed setting

**Cache Benefits:**
- Instant replay of sentences
- No repeated API calls (saves cost)
- Works offline after first generation
- Faster navigation through read content

> **📘 Technical Details:** See [Preload & Cache Audio](technical/preload-cache-audio.md) for the three-layer caching architecture (In-Memory → IndexedDB → S3).

**Cache Invalidation:**
- Changing TTS provider
- Selecting different voice
- Adjusting playback speed
- Manual cache clear in settings

**Storage:**
- Cached in browser (IndexedDB)
- Approximately 5-10KB per sentence
- 100 sentence chapter ≈ 500KB-1MB
- Managed automatically (old entries cleared)

## Preloading Strategy

**How It Works:**
- While sentence N plays, system loads N+1 and N+2
- Loads happen in background
- No impact on current playback
- Ready instantly when user advances

**Priority System:**
1. Current sentence (highest priority)
2. Next sentence (medium priority)
3. Sentence after next (low priority)

**Smart Cancellation:**
- If user jumps ahead (e.g., sentence 50 → 100)
- Cancels loading of sentences 51-99
- Immediately starts loading sentence 100
- Prevents wasted API calls

## Provider Architecture

**Common Interface:**
- All three providers (Google, Polly, ElevenLabs) work the same from user perspective
- System abstracts provider differences
- Consistent experience regardless of provider
- Easy switching between providers

**Provider Differences:**
- Voice quality and characteristics
- Pricing and free tiers
- Available languages
- Word timing accuracy
- API reliability

**Why Multiple Providers:**
- Redundancy (if one fails, switch to another)
- Cost optimization (use free tiers)
- Quality options (premium vs standard)
- User preference (voice characteristics)

## Auto-Play Mechanism

**How It Works:**
1. Audio element fires "ended" event when sentence finishes
2. System detects event
3. Increments to next sentence
4. Triggers playback of next sentence (already preloaded)
5. Updates visual highlighting
6. Scrolls to keep sentence visible
7. Preloads next sentences in background

**Skip Logic:**
- Checks if next element is image or text
- If image: Skips to following text element
- If chapter end: Shows completion prompt
- Maintains smooth flow

**Why It's Seamless:**
- Next audio preloaded (no delay)
- Event-driven (immediate response)
- Visual updates synchronous with audio
- No gaps between sentences

> **📘 Technical Details:** See [Auto-Play Sentences](technical/auto-play-sentences.md) for the complete implementation with intent tracking, navigation logic, and declarative play triggers.

## Error Recovery

**Retry Strategy:**
- Attempt 1: Immediate
- Attempt 2: Wait 1 second
- Attempt 3: Wait 2 seconds
- If all fail: Show error to user

**Fallback Options:**
1. Use cached audio if available
2. Suggest switching provider
3. Skip to next sentence
4. Disable TTS temporarily

**User Communication:**
- Clear error messages
- Actionable options
- Non-blocking (can continue reading)
- Dismissible notifications

## Performance Characteristics

**Playback Latency:**
- Cached audio: <50ms (instant)
- First-time generation: 500ms-2s (depends on provider)
- Network factors: Variable

**Highlighting Accuracy:**
- Word-level timing: ±50ms typical
- Adjustable offset for fine-tuning
- Varies by voice and provider
- Generally imperceptible to users

**Memory Usage:**
- Active sentence audio: ~100KB
- Preloaded sentences: ~200KB
- Cache (100 sentences): ~1MB
- Cleaned up automatically

**Network Usage:**
- Per sentence API call: 1-5KB request
- Audio response: 10-100KB (depends on length)
- Metadata: <1KB
- Cached sentences: Zero network usage

## Why It Feels Fast

1. **Preloading**: Next audio already loaded
2. **Caching**: No repeated API calls
3. **Parallel Requests**: Multiple sentences load simultaneously
4. **Optimized Rendering**: Smooth word highlighting (60fps)
5. **Smart Prioritization**: Current sentence loads first

## Technical Limitations

**Provider Limits:**
- API rate limits (requests per minute)
- Monthly character quotas
- Concurrent request limits
- Geographic restrictions

**Browser Limits:**
- Audio format support
- Cache storage quota
- Network request limits
- Audio playback restrictions (mobile autoplay)

**Quality Trade-offs:**
- Higher quality voices = Higher cost
- Faster speeds = Less natural sound
- More preloading = More API calls
- Larger cache = More storage used
